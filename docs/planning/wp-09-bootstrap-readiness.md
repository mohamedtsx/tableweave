# WP-09 initial-domain adoption readiness

for a later combined-source feasibility fixture. No API change, implementation or

## Initial adoption is not an old-domain reset

The controller supports explicit accepted selected IDs; empty selection is the
omitted-value default, not a mandatory mount reset. A same-domain pending proposal
must not be accepted/rejected/replayed merely to mount. First publication completion
still calls the captured retirement port and requires acknowledgement. That port
acknowledges actual obsolete-domain obligations, not unconditional destruction of
valid current-domain state. No general no-op retirement port is approved.

An application-owned stable bundle holds the genuine native controller, actual
controller.getDefinition() reference, registered native definition, domain incarnation
and real pending receipt history. Outside render/mutation/notification, a private
one-use initial certificate must positively establish:

- Accepted state and any actual pending receipt belong to the current incarnation.
- No unretired predecessor-domain/source/editor/action obligations remain.
- Expected/actual allowing context is current. Equal keys, revision0, query identity,
  IDs, previous=null or epoch1 alone establish no ownership.
- The real owner has reconciled receipt bookkeeping after dispatch returned.

The owner calls begin, binds its certificate to the exact publication/ticket/candidate
and incarnation, then calls complete. The existing captured retire callback still
runs. Only for that exact certified initial transition may it consume the certificate
and acknowledge an empty obsolete-domain obligation set without controller mutation.
It rechecks accepted-state/receipt generations and provenance; failed/reentrant/
stale/revoked outcomes cannot recycle the certificate. Verify actual settlement.

Accepted query/selection/revision/callback counts and the exact pending receipt
remain unchanged by adoption. Later normal acceptance still revalidates command,
clock and definition constraints; preservation guarantees no freshness. No accepted
mirror, getPending method or controller wrapper is added.

## Resets, external ownership and lifetime

Real context/definition/access changes, explicit same-context resets and admitted
disposal retain deny-first cleanup, reject of actual old pending intent **before**
real accepted selection clearing, owed participant cleanup and acknowledgement only
after actual successful outcomes. Proposed-only/rejected/busy work is not clearing.
Never accept an obsolete query proposal merely with an empty-selection override.

Unknown external history means adoption is unavailable without mutating its state.
Require the real owner's provenance or explicit owner-authorized retirement. Never
infer preservation or silently clear as fallback. Borrow an existing current bundle
without another begin or competing publisher.

UI event authority is separate from the bare application-owned cleanup route. Do
not install a blanket publication-ready validator that blocks mandatory cleanup
while publication is denied. Native validation remains mandatory; extra application
validators must explicitly support the owner's narrow lifecycle operations. This
adds no bypass flag/public retirement mode or permission to overwrite validators.
Notification failures cannot undo a completed accepted reset.

The application owns publication/controller lifetime. Ordinary view Strict/Suspense/
unmount cleanup releases exact local participants/config/subscriptions, not accepted
state or the application domain. On lifetime end, finish publication retirement
before disposing the controller. Server/client owners reconstruct provenance
independently: authorities, receipts and certificates are not serialized credentials.
Prefer authorized initial selected state in the constructor seed; getServerSnapshot
remains that constructor snapshot. Static projection is separate from event permission
and publication settlement is not proof of committed callbacks/frame/hydration.
